# Features — current capability map

> **What this is**: the living list of what Classroom can do TODAY — for
> humans who forget and sessions that plan. Current state only, not a
> changelog (git history has the story).
>
> **Maintenance rule**: any feature-visible change updates this file in
> the SAME commit. Add the row, update the row, or move it to "Cut" when
> a decision kills it.

> **Vocabulary of the product itself (updated 2026-08-30)**: a **Book** is a CONTAINER — it holds decks, notes, and whether you read it. A **Deck** is an ordered list of words and the thing you actually drill (word decks, and **sentence decks** — cloze cards testing the same words in context). **Official books** are ours, reachable as the "Official" tab. **Reading list** is a FILTER over books (`readAt` set), not a separate kind of thing.
>
> The 2026-08-30 merge is what made this true. Until then `study_books` was the reading list while `study_vocab_lists` was shown to learners as "Books" — two tables, one word, in a product whose stated rule is one word one meaning. The 2026-08-29 naming pass killed "Dictionary" and "Curated lists" and walked straight past this one.

## Self-study — home & search (`/home`, `/search`)

- **Home** (2026-08-29) — what you land on when you open the app with no particular plan. Every other page answers "where is my stuff" (Books manages collections, Decks lists what you can drill, Sentences manages cards); none of them answered "what should I do right now", which is the question someone opening the app at 8am actually has. Home owns nothing — every tile links into a surface that already existed
- **Spotlight** — when anything is due, a gradient panel leads the page: the count, one line of context, and a single white "Start reviewing" pill. A home page whose loudest element is a list of links has no centre. It renders ONLY when cards are actually due — an always-on banner stops being information — and when it's there the header drops its own Review button and its subtitle, because three copies of one sentence is worse than one. **Two shapes** (2026-08-29): stacked on a phone (4rem count, full-width CTA beneath it), a BAND from lg (3.5rem count inline with "N cards ready to review", then the fanned decks, then the CTA). **The band fans the actual decks** (2026-08-29): up to FOUR real covers for the decks that genuinely have cards due, overlapped and splayed ±10° from the centre so they read as cards held in a hand, and **each is a link straight into that deck**. A count says how MUCH work is waiting; the covers say what the work IS, in the same artwork the learner recognises from the shelf below — real decks, never a decorative stack, because something that looks this much like a card WILL get clicked and a picture that doesn't respond is a broken promise. Hover/focus pulls a card straight, lifts it and brings it to the front, so an overlapping fan stays readable while you point at one. Rotation and depth ride CSS VARIABLES (`--fan-rotate`, `--fan-z`), not inline `transform`/`z-index` — inline styles outrank utilities, so hover classes could never have undone them. Desktop only: on a phone the band is already a stack and the fan would push the CTA below the fold. It runs the FULL page width like the shelves — a `max-w-5xl` cap was tried and reverted, because the band was never the problem: the PAGE was out of proportion (a 320px rail against an 1800px content column), so everything right of the sidebar read as over-stretched. The fix belonged in the shell, not in a cap on one element that would then disagree with every row beneath it. One shape did not survive both ends — stacked at desktop width it became a 233px slab with its text in one corner and its button in the other and a thousand pixels of empty gradient between; a wide short band reads as a banner, a wide TALL one reads as a layout that broke. The same rewrite fixed a phone bug with one root cause: `flex-wrap` never wrapped, because the CTA is `shrink-0` while the text column is `flex-1`, so at 390px the column collapsed to 87px and "cards" — in a row that cannot wrap — overflowed 5px UNDER the button. Explicit `flex-col` up to lg fixes both ends at once
- **Sentence decks get their own shelf** (2026-08-30) — sentences used to be ONE tile in the first row, which could say that cards exist but never which BOOK made them, so drilling one book's sentences meant leaving Home for Decks. Now a row of its own directly under the word decks (All sentences first, then a deck per book that has cards, playable ones first), because the two card types are the two halves of one loop. The spotlight's fan draws from BOTH shelves — it's about what is due, not about which row a deck lives on
- **Recommended sentences** (2026-08-30) — `Turn these into sentences`: books that have words and NO cloze card yet, largest first. Same rule as the official-book row — real signal, no model, and it can say why it is there. A book that already has cards is deliberately absent: repeat presses EXTEND coverage, and that button lives on `/sentences`, so recommending it here would be a row that never empties
- **Four rows, in the order a learner wants them** (2026-08-29, the shape streaming home pages converged on): **(1) yours, favourites first** — All words on the liked tile leads, then Sentences, then decks sorted by due count, each with a due badge on the cover and a play overlay ONLY where there's something to drill (a play button that opens an empty session is a broken promise); capped at six. **(2) recommendations that can say why** — `Because you're learning Japanese`: official books in a language the learner already studies, minus the ones they already own (importing a pack creates a DECK named after it, so a name match against the learner's decks is the honest "already have this" signal). No model involved — an unexplained recommendation is just an advert. **(3) recents** — the last four chats that have actual messages in them (an empty draft thread is not something to pick up), on generated tiles so the row reads as a shelf rather than a text list wedged between two shelves. **(4) the whole catalog**, for when none of the above was it
- **Shelf scale** — `components/study/shelf.tsx`: 1.5/1.875rem bold section titles and 168/196px artwork. The shelves ARE the content; body-scale headings made the page read as a settings screen with pictures on it. `ShelfCard` is the shared item (artwork · name · state · optional badge/play), used by all four rows
- **Shelves take the whole page** (2026-08-29) — every shelf row (Home's four, Books, Decks) used to sit in a `max-w-3xl` box inside a `max-w-6xl` shell, so on a wide monitor covers were CLIPPED at 768px with hundreds of pixels of empty page beside them — and Official, the one row that sat outside the box, was inexplicably wider than the rest. The cap is gone, shelf landings render `PageShell width="wide"` (`max-w-[1800px]` — a ceiling for ultrawides, not a measure), and `OfficialShelf` is spacing-neutral so its callers place it. Artwork is not prose: the wider the window, the more shelf you should see
- **Shelf ‹ ›** (2026-08-29) — paging arrows in the section HEADER beside "See all", desktop-only, rendered only when the row actually overflows, dimmed rather than removed at each end (a control that vanishes mid-row makes its neighbour jump). Header, not floating over the artwork: covers come in two aspect ratios (`aspect-square` collections, `aspect-[3/4]` pack spines), so an overlay centred on one is off-centre on the other. Scroll position is READ from `scrollLeft` through a `ResizeObserver`, never asserted, so the buttons stay honest through resizes, a row that grew a card, and momentum scrolling. Touch keeps the gesture — a pair of dead buttons is worse than none
- **Search** — a field at the top of Home, and its own `/search` page. One query over the learner's words (term, reading AND meaning — half the time you remember the English), their sentence cards with blanks filled in, their books, their chats, and the catalog — including **the words inside each official book**, which answers "where could I learn this". Results are grouped and a word shows its meaning inline: for a dictionary lookup the answer is READ, not navigated to. A page rather than a dropdown, because a popover that vanishes on blur is hostile to reading. **Pinned on desktop** (2026-08-29): the field lives in a sticky top bar (`components/shell/study-topbar.tsx`) present on every study page, not in the body of two of them — it used to scroll away the moment you started reading and simply didn't exist on Books, Decks, Sentences or a chat. On `/search` the pinned field carries the query, so the bar reflects the page under it. Phones keep it in the page body (`lg:hidden`): the top edge there is already spent on the hamburger navbar, and the bottom tab bar covers re-entry. It FLOATS like the sidebar panel — inset, rounded, `shadow-card`, `bg-surface/70` over `backdrop-blur-xl` — rather than a flush band with a bottom rule, so the two pieces of chrome read as one system; the glass is load-bearing, since content scrolls UNDER a sticky bar and should stay faintly visible instead of vanishing behind an opaque strip. **Two layers**: a full-width SCRIM sits behind the bar (a `color-mix` wash of `--bg`, ~92% at the top edge, gone 2rem below the bar). An inset bar has gaps — 8px above it, 8px to its right — and content travelled through those unmuted, so mid-scroll a row of covers looked sliced off above the bar. The scrim covers the whole strip, gaps included. A mix rather than a solid, because solid would darken correctly and throw away the glass the bar exists to have; mixed from the ground token rather than black, so light mode gets a light wash. The space it OCCUPIES is PUBLISHED as `--study-topbar-h` (**4rem** at lg — 3.5rem of `h-14` bar plus the 0.5rem it sits down from the top; **0 below**), mirroring `--study-tabbar-h` at the other edge, so the full-height chat pane sizes around whichever bar exists with ONE expression
- **Hover is calm** — covers brighten, they don't lift. A `-translate-y` on shelf artwork makes a whole row bob as the pointer crosses it, which reads as a wiggle rather than feedback (2026-08-29)
- **Nav** — sidebar row ABOVE "New chat" (what to do comes before what to say) and the first tab in the phone bar. The PWA `start_url` still opens `/chat`

## Self-study — books, decks & sharing (`/books`, `/decks`, `/b/<token>`)

- **A book is a container** (2026-08-30, migrations 0019+0020) — it holds decks, notes, and whether you read it. `study_vocab_lists` → `study_decks` (+ `book_id`, nullable — a loose deck is still legal, because forcing a container first is the friction that stops people saving the word); `study_vocab_list_items` → `study_deck_items`; `study_sentences.list_id` → `deck_id`. The tell that the merge was right: **`study_notes.book_id` already pointed at `study_books` and did not have to move** — notes were hanging off the right table the whole time, there just wasn't a deck beside them
- **The rename migration is hand-written** — drizzle-kit prompts "created, or renamed?" and cannot answer it non-interactively; letting it guess emits DROP + CREATE, which reaches the same end state by destroying every word, every deck membership and every card's review history. 0019 is renames only (its snapshot produced by applying the same renames as string substitutions), 0020 is the additions drizzle generated against that truthful baseline, plus a **backfill giving every existing deck a book of the same name** so a learner's shelf looks identical the morning after
- **Deleting a book never takes the contents** — both FKs are SET NULL: decks come loose with every card's review history intact, notes become standalone notes. The confirm names what SURVIVES rather than saying "cannot be undone", which would be both scarier and less true. Its own e2e test, because it is the least forgivable failure the model has
- **Read-only share links** (`/b/<token>`) — a revocable capability URL, the same shape as the student portal's `/p/<token>`: a pattern this codebase already has, tests, and knows the failure modes of. The public query returns a fixed SHAPE rather than a row, so a column added to `study_books` later cannot leak by being added; a revoked link and one that never existed both 404, because "this used to exist" is information the owner didn't agree to share. **Copying is a COPY, not a live link** — two people studying the same material diverge within a week, and a synced book would mean one person's pruning deletes the other's cards. Review history is deliberately not copied: starting someone mid-schedule tells them they know words they have never seen. Collaborative editing stays a separate arc behind the open realtime-transport decision
- **Deck records and the platinum trophy** (`study_deck_runs`) — the drill used to end on a blank "nothing due" screen, which is the least interesting moment to say nothing: the learner has just done the work and is deciding whether to come back tomorrow. A finished run now shows accuracy, longest streak, and your best over that deck; the deck page keeps the record board. Only COMPLETED runs count (an abandoned session is not a record), and **cram rounds are excluded** for the same reason they are schedule-neutral — otherwise the route to a perfect score is re-drilling the easy deck. **Platinum = every card in the deck mastered**, itself derived from review evidence, so it cannot be farmed by one good day; an empty deck never earns it
- **The error deck** (`/decks?errors=all`) — only the cards whose MOST RECENT answer was "again", within 30 days. The single highest-value drill there is and the one Anki makes you hand-build a filtered deck for: a due deck is mostly cards arriving on schedule that you already know. "Most recent" and "within a window" are both deliberate — a card you failed last month and have since got right three times is not a live problem, and a deck that never empties is one people stop opening. Graded for REAL, not as a cram: the whole value is that getting one right now moves it. This is what the review log was for; the card row knows its schedule, only `study_reviews` knows what you answered

## Self-study — learning path & progress (`/path`, `/progress`)

- **Learning path** (2026-08-30) — the only surface with an opinion about ORDER, which is the thing a beginner cannot supply for themselves and the reason self-study stalls in month two: not lack of material, lack of a next thing. Product-shipped content (`src/content/study-paths.ts` → `study_paths` / `study_path_steps`, seeded by `db:seed:paths`, which also runs on every deploy and FAILS on a step pointing at a pack that doesn't exist). Steps mix card work with human work on purpose — learn the words, drill them in context, use them with the tutor, then with a person; a path that is only flashcards teaches someone to recognise words they've never said out loud
- **The path is a SKILL TREE** (2026-08-30, `components/study/path-tree.tsx` + the pure layout in `lib/study-path-tree.ts`) — one trunk, three limbs growing up from a root that is the path itself, in the Arc Raiders idiom: hub circles with a headline number beside them, nodes budding up each limb, and the limb filling in with its own colour as the work lands. It replaced a numbered spine that was honest and unreadable — a column of equal rows where the only thing visible from across the room was which one was highlighted. **The tree can say the thing the spine could not: which KIND of work you have quietly stopped doing.** That is a whole limb sitting grey, and it is the most useful single fact a learner can have about their own study
- **It is drawn as a GIT GRAPH, and that is the whole visual argument** — cables run in straight orthogonal legs with rounded elbows (up, across, up), never free-flowing curves; every one is the same weight; nodes are SOLID discs with a glyph, filled in the limb's colour once they're yours and a flat dark puck until then; each carries a small `3/10` rank pill on its bottom edge, and **nothing else**. **Colour arrives as FILL, never as an outline** — a node you have started, a node you have finished and the limb's hub are all solid, with the glyph cut out in near-black (`--on-brand`, which flips with the theme); only the one node marked "start here" is a ring, because it is the only node that has to be loud without being finished. A tinted outline said "almost" about work the learner had genuinely started, and it is why the first cut read as washed out next to the reference. The first cut got all of this wrong in the same way — bezier cables with a personality each, thin outlined rings, and a two-line caption under every node — and it read as a diagram somebody had typed over rather than a tree. **Per-node captions are what a tree cannot carry**: the title lives in an INSPECTOR in the card's corner that names whatever the pointer or keyboard focus is on (a floating tip gets sliced in half by the canvas edge), and in the panel a click opens. Between hovers the inspector carries the one thing the tree has to say about itself — that nothing on it is locked
- **The trunk is long, and it splits low** — a single unbroken stem runs 150px straight up out of the root before the three limbs peel off it. Long on purpose: that stem is what makes the thing read as one tree rather than three columns sharing a bottom edge. And low on purpose — split at the halfway point and the horizontal run lands at exactly the hubs' own height, drawing a line straight through all three of them. For the same reason each hub's name and headline number sit BESIDE its disc, on the outward side: under it, they shared an axis with the cable
- **Three limbs, and the branch is DERIVED from the step's kind** — `pack → VOCABULARY` (green), `sentences → GRAMMAR` (amber), `chat`/`lesson` → `CONVERSATION` (the `--practice` rose). No `branch` column: the kind already says what evidence completes the step, and a second field could only ever disagree with it. **GRAMMAR is measured by cloze evidence, and that is a stated compromise** — a cloze card is the only production-in-context measurement the app has, and supplying the right word in the right slot is most of what beginner grammar is. A real grammar-point catalog is the honest upgrade; when it exists, only the kind→limb mapping changes
- **Nothing is locked, and the geometry may not imply otherwise** — a skill tree is the visual language of gated progression, which is exactly the product we said we would not build. So every node is a live button whatever its state, no node is ever `disabled`, and there is not a padlock in the codebase. Dim means "you haven't done this yet", never "you may not" — even the untouched nodes carry a whisper of their limb's colour, because three limbs of identical grey circles is a diagram, and pure grey read as unavailable. What the tree encodes is ORDER and KINSHIP, never permission. ONE node says "Start here" — the first INCOMPLETE step, not the one after the last completed one, so a learner who jumped ahead is still pointed back at the foundation they skipped
- **Every node opens onto its own MICRO-NODES** — a sheet (right at lg, bottom on a phone, so the tree stays visible behind it: half of what opening a node tells you is where it sits) carrying the step's own detail, its bar in its own unit, and one circle per REAL item behind it — every word in the book with whether you know it, every word of yours still missing a sentence card, ten circles for ten messages with six lit. Loaded on demand through a server action, never with the page: eleven nodes would otherwise pull several hundred rows to colour eleven circles, and a learner opens two. Tapping a micro-node names it in a caption UNDER the grid rather than a tooltip — half the audience is on a phone, where hover does not exist. Hubs open too, onto the limb's claim and its nodes; a big number nobody can drill into is the kind of statistic this app refuses to print
- **It pans, zooms and does not trap your scroll** — drag, pinch, ctrl+wheel, and a fit control. Wheel panning stops claiming the gesture the moment the canvas hits its edge, so the page keeps scrolling (the scroll-chaining lesson the mobile drawer learned the hard way); when the tree fits, it is locked centred, because there is nothing to pan to. **Every desktop and tablet width shows the WHOLE tree, measured rather than assumed** (`treeprobe` sweep, 2560/1800/1440/1280/820 wide: 15 of 15 circles inside the canvas). Below the scale where a node stops being a target the canvas opens FRAMED ON YOUR NEXT NODE and pans instead — which is the phone, and only the phone. Keyboard focus moves the camera (tabbing to a node you cannot see is a broken tree); a pointer click never does (nothing is more disorienting than the view jumping under the thing you just aimed at)
- **Targets have to be reachable** — `seed-paths.ts` now fails when a pack step asks for more words than the book contains, the same way it fails on an unknown slug. We shipped that bug: "learn 20 words" against a 15-word book, invisible in a list of rows (it just sat at 15/20 forever) and on a tree a node that can never light up, which reads as the app being broken
- **One word, one count** — `study_vocab` has no unique index on (learner, term), so joining a pack to a learner's vocabulary ON TERM could return one pack item twice and inflate every number on the page. Deduped by term, best status winning: if one duplicate survived a return, the learner knows the word
- **Progress is DERIVED, never stored** — no "current step" column. The moment one exists it can disagree with the review history, and then either the number is wrong or the learner is told they haven't done something they did. Consequence worth knowing: rewriting a path's steps is SAFE — progress doesn't hang off step ids, so the seed replaces them wholesale and every learner's position re-derives. Per-step evidence: words at `reviewing`+ from that book (matched on TERM, so someone who already knew 猫 isn't punished for it), cloze cards known, messages sent, lessons attended
- **Following a path is a bookmark, not a state machine** — there is no "complete this step" action, because nothing a learner could press would be true. Following is what lets Home point at ONE path; a home page suggesting three curricula has made a menu, and the learner who needed guidance is exactly the one who can't choose from it
- **`study_reviews`** (2026-08-30, migration 0018) — one row per graded answer, written by the single grading funnel (`lib/srs-review.ts`) so a new card type cannot be added that forgets to log. The card row knew when it was next due; nothing knew whether the learner showed up on Tuesday. Both card FKs are SET NULL — deleting a word must not erase the fact you practised that day
- **Progress page** (`/progress`) — words and sentences you KNOW (reached `reviewing`/`mastered`: it came back on a later day and you still had it — recognising a word ten seconds after reading its meaning doesn't count, which is why this number is smaller than the word count and worth more), 30-day recall, streak, a 14-day column strip, and both pipelines on the teacher side's own `viz-*` idiom. **No level, no grade, no model-written assessment** (the standing "AI-asserted level jumps" cut): a number a learner can't trace back to something they did is worse than none, because the first time it disagrees with how they feel they stop believing all of them. **Recall shows "—" under 10 graded answers** — a statistic that swings ten points on one miss is not information. The streak doesn't break on a day that hasn't ended yet

- **Rewards, each showing its receipt** (2026-08-30) — every badge states what earned it in the learner's own numbers ("38 cards you've recalled on a later day"), never a title alone. That is the difference between a reward and a sticker: a learner who can trace a badge will believe the next one. No locked/greyed rows — a list of things you failed to do is not a reward shelf. Retention is the one badge with a floor on evidence, because 100% off four answers is a small sample, not an achievement
- **What you have the words for** (2026-08-30) — the honest answer to "tell me which area I can have a conversation in". It says *"you know 38 of the 45 words in Café survival French — enough to order, ask for the bill, and follow the answer"*: a COUNT of cards recalled on a later day, plus a fixed description we wrote for that topic. It never says "you can hold a conversation", because that is a claim about a person we have never heard speak. **Coverage of a topic is checkable; proficiency is a guess** — the wording is load-bearing, not decorative, and it is how this coexists with the standing "no AI-asserted levels" cut. Matched on TERM, so someone who already knew 猫 isn't punished for it

## Teacher workspace — accountability

- **Between lessons** (2026-08-30) — the founder's reframing of the tutor role: *"the tutor is more of a motivation and person who will push and really check up whether the student really progressed, not just teaching — because AI already teaches and explains well, but it makes learners lazy."* A model will explain the same point for the ninth time at 2am and never ask why you're asking again; it never notices you haven't opened the app in eleven days; it cannot be disappointed. Those aren't defects — they're the parts of teaching that need a person
- **What the card shows** — days studied out of the last 14, reviews, newly-known cards, and the flags worth opening a lesson with: days since the last review, saved words never reviewed once (**the most common way self-study fails, and invisible from inside — the shelf looks like progress**), recall under 70%, and the five words beating them most. It leads with the uncomfortable numbers rather than the flattering ones, and phrases every one as an OBSERVATION a tutor can raise, never a verdict: "studied on 3 of the last 14 days" is a fact two people can discuss; "not committed" is a label the learner would be right to resent. It reads the SAME evidence the learner sees on their own `/progress` page, so a lesson starts from one shared set of facts rather than two accounts of the same fortnight. A hand-typed student with no learner account simply shows nothing — a normal state, not an error

## Self-study — book a tutor (`/tutors`, `/browse`)

- **The tutor pilot** (2026-08-30) — the first bridge between the app's two halves. The teacher workspace has had a schedule, a lesson loop and a student record since day one; the learner had no way to reach a human. Deliberately NOT a marketplace (that stays cut until teacher density): no ratings, no ranking, no review counts — those are the machinery of a two-sided market, and adding them early is what turns a tutor directory into a race to the bottom on price. Order is the order they joined
- **A booking becomes an ordinary lesson** — the first booking creates (or matches, on email) the learner's row in that tutor's roster, and a paid booking writes a normal `lessons` row. From there the whole existing teacher loop — agenda, prep sheet, records, homework, recap, portal — works on it with no special-casing, because they are just another student. The focus answers land in `nextLessonFocus`, which the prep sheet already reads
- **Slots are real instants** — availability is a weekly pattern in the TUTOR's timezone (`weekday` + minutes-from-midnight), resolved through `@date-fns/tz` so "9am in Tokyo" is the right instant in July and in January. Learners see their own zone because the browser formats an instant. Day-walking, not +24h: a DST week is not 7 × 24 hours. `buildSlots` re-derives on the server and the booking action checks membership — a client-supplied time is a request, not a fact
- **The booking modal asks what the lesson is FOR** — a closed set of focus chips plus a free note, and it arrives PREFILLED from the last booking with that tutor. A form that only takes a time produces a lesson whose first ten minutes are spent working out why anyone is there; and re-typing "conversation, past tense" every fortnight is the small friction that quietly ends a habit
- **One lesson or a standing weekly slot** — recurring is billed monthly at a discount (`TUTOR_RECURRING_DISCOUNT_PERCENT`, default 10%). Not generosity: a standing hour is the scarcest thing a tutor sells, the learner is paying for certainty as much as teaching, and both sides are better off when that trade is priced. The next four lessons go on both calendars as soon as it's paid
- **Browse** (`/browse`) — search answers "where is the thing I can name"; this answers "what is there", which is the question you have when you finish a book. Books by language (languages you already study first), tutors grouped by region, then the guided paths. **Country is the TUTOR's, never a book's** — there's no honest way to say a vocabulary book is "from" a country, and inventing that facet would make the page look richer while telling the learner nothing true

## Live lessons — the in-app call (`/call/<bookingId>`)

- **The call is the input; the learning context is the product** (2026-08-30) — we rent the pipes and own the artifact. Preply uses Agora, italki lets tutors use Zoom; neither built WebRTC and neither should we. The reason to own the call is not call quality, it is **access to permissioned lesson audio**: `study_reviews`, `/progress`, the accountability card and the prep sheet already exist, so a lesson can become EVIDENCE rather than a recording nobody rewatches
- **The room belongs to the LESSON, not to a paid booking** (`/call/<lessonId>`) — binding it to `tutor_bookings` made the room unreachable in every environment we run, production included: no environment has Stripe configured, so a tutor cannot be listed and a booking can never reach `confirmed`. It also excluded the case the teacher workspace has served since day one — a teacher and a student they scheduled themselves, with no money involved. Nothing is lost from the tutor pilot, because a confirmed booking already writes a `lessons` row and reaches its room through the same door. `lesson_calls.lesson_id` is UNIQUE, so a dropped connection rejoins the room it left instead of opening a second lesson
- **Who may enter** — the teacher is matched on WorkOS user id (emails change, and a tutor who updates theirs must not lose their own room). The student is matched on WorkOS user id FIRST, then on **email** — not a fallback bolted on, but the product's own claim mechanism, and load-bearing here: an account that already has a teacher row always resolves as a teacher, so a teacher sitting in someone else's roster never gets a `workos_user_id` written on that student row and would otherwise be locked out of a lesson plainly theirs. That is the founder's own account. "No such lesson" and "not yours" return the same message, or the error becomes an id oracle
- **Nothing records before both people agree** — consent is stored per side WITH A TIMESTAMP (`teacher_consent_at`, `learner_consent_at`), not as one boolean, because "both agreed, and when" is the claim we would have to stand behind. The server refuses to start recording otherwise; a client that decides when recording may begin is a client that can be made to lie about it. `record_on_start` is never true — it would start recording at the moment of joining, which is exactly the invisible recording we promise not to do. You can join without agreeing; the lesson simply is not recorded
- **Separate audio per person, which is the whole point** — track recording writes one WebM per participant, so speaker identity is a fact rather than a model's guess about who was talking, and overlapping speech stays separable. Verified end to end before any of this was built: two browsers, two files, distinct checksums, copied into our own R2 byte-identical
- **Status is not evidence that a lesson was captured** — a track recording whose participant allowlist matches nobody still reports `UPLOADED`, with a real duration and no error, and contains ZERO files. That is why `lesson_recordings.expected_track_count` exists and why the action refuses to start with fewer than two people in the room. **`user_ids` means RealtimeKit's participant id, not our `custom_participant_id`** — the docs' `["user-123","user-456"]` example reads like an application-side id and is not one; passing ours is what produced the silent empty recording
- **Explicit states, not nullable fields** — `lesson_recording_state` runs `awaiting_consent → recording → recording_complete → ingesting → ingested → …`. `ingesting`/`ingested` are ours, not the provider's: RealtimeKit keeps track files in ITS bucket behind presigned URLs that **expire after seven days**, so until the bytes are copied into our R2 and checksummed the artifact is not ours and the lesson is one outage away from gone. Nothing downstream may start before `ingested`
- **The webhook is authenticated and idempotent** — `rtk-signature` is RSA-SHA256 over the RAW bytes (reserialising the JSON changes them and every signature then fails). The key document is **not a JWKS** despite the URL: it is one RSA key in PEM SPKI form, and importing it as a JWK fails silently in a way indistinguishable from a forgery. Deliveries are claimed by `rtk-uuid` in a table with a unique index BEFORE anything acts, so a retried `UPLOADED` cannot start a second ingest. The `UPLOADED` payload carries the expiry but **not** the download URLs, so the pipeline is always webhook → fetch recording → copy
- **A 1:1 room, not a meeting app** — no participant list, no grid, no stage management, no chat panel. Device preview and input pickers before joining, because a call you join without seeing yourself starts with "can you hear me?" every time; then mic/camera, connection quality, and a recording indicator that never leaves the screen while it is on
- **Not built yet, deliberately**: ingestion into R2, transcription, utterance storage and learning-artifact extraction. The extraction and teacher-approval loop **already exists** for pasted notes (`lib/ai/extract.ts`, `lessons.aiDraft`, `applyDraft`, and `lesson_source_type` already carries `transcript`/`audio`) — the remaining work feeds it a real transcript rather than building a second pipeline. Evidence will anchor on stable **utterance ids**, never on model-written timestamps, which a model can invent
- **Cut for this release**: group classes, livestreaming, full lesson playback, VOD, DRM, creator payouts, live captions, screen sharing, AI in the call

## Self-study — payments (Stripe Connect)

- **Money never sits with us** — tutors onboard to their own Stripe **Express** account; a lesson is a **destination charge** with our commission taken as `application_fee_amount`. We collect no bank details and hold no KYC obligations, which for a handful of tutors is not a shortcut but the only defensible option
- **The split, and who pays Stripe** — learner pays gross; tutor receives `gross − platformFee`, EXACT and knowable at charge time; we receive `platformFee − stripeFee`. We deliberately do NOT set `on_behalf_of`, which would make the tutor merchant of record and push card fees onto them the way most marketplaces do: Stripe's fee isn't knowable when the charge is created, so that would make every tutor's earnings an estimate until settlement. **We take the variable number so theirs is exact.** `tutor_payments.stripeFeeCents` is nullable and filled in from the balance transaction on `payment_intent.succeeded`; until then OUR margin says "estimated" and means it
- **Every party's share is stored, not derived** — fees change, and a history that recomputes from today's rates lies about last month. Booking price is stamped at booking time too: a tutor raising their rate must never silently reprice an hour someone already holds
- **Fee transparency on both sides** — the tutor's page shows the learner what the tutor receives before they pay; the payouts page shows the tutor that they keep `100 − fee`% and that we cover processing out of our share. Payment history for both: `/tutors/bookings` (learner) and `/teaching/payouts` (tutor)
- **The webhook is the single writer** — a `success_url` proves someone closed a tab, not that money moved, so nothing downstream of a redirect confirms a booking, writes a lesson or touches the ledger. Retries are idempotent (unique index on the payment intent; the lesson is skipped if the booking already has one), and a failed handler returns **500 so Stripe retries** — swallowing it would leave a learner charged for a lesson that never reached a calendar. **Study Pro is guarded from it**: tutor subscriptions carry `teacherId` metadata and are claimed before `applySubscription` runs, or buying a weekly lesson would have handed out Study Pro
- **Payouts gate the listing, with no override** — `setTutorListed` refuses to publish a tutor Stripe hasn't enabled, and `account.updated` un-lists one who loses payouts. The worst failure this feature has is taking real money from one person for a promise we can't keep to another
- **Cancelling does not refund** — the booking is cancelled and the tutor's calendar freed; the payment row stays exactly as it was. A no-questions instant refund on a lesson starting in an hour makes a calendar worthless, and a pilot needs a human deciding, not a policy engine. Refunds mark the row `refunded` rather than deleting or silently netting it out — a refund is something that happened
- **`scripts/seed-tutors.ts` refuses to run against a remote database** — it sets `payoutsEnabled`, which only Stripe may set for real money; a seed that could flip it in production would turn the guard into a suggestion

## Self-study — sentence cards (`/sentences`)

- **The second card type** (2026-08-29) — a word card asks what a word means; a **cloze sentence card** asks whether you can still supply it when a sentence needs it. Own table (`study_sentences`, migration 0016), own SM-2 schedule (the two decay at different rates and averaging them would hide both), own sidebar row and own shelf on Decks. `vocab_id`/`list_id` are SET NULL, never cascade — deleting a word must not destroy sentences you've been reviewing for weeks
- **Generated, not hand-written** — "Make cards" (from All words, or one book) turns words that have no card yet into cloze sentences, oldest-first, 8 at a time, one model request per language. Almost nobody writes cloze cards by hand, which is exactly why this is worth doing for them. Repeat presses EXTEND coverage instead of duplicating it (LEFT JOIN … IS NULL, not a NOT IN subquery). Deterministic offline generator when no `OPENAI_API_KEY`, so dev + e2e exercise the whole pipeline
- **The blank is placed by US, not the model** (`src/lib/cloze.ts`) — the model returns sentence and target word SEPARATELY and `markCloze` wraps it; a card whose target isn't in its own sentence is DROPPED with a warning, never patched. A cloze card with the blank in the wrong place teaches the wrong thing, which is worse than one fewer card. Storage is Anki's `{{…}}` convention in the text (survives hand-editing; can't drift out of sync the way character offsets can), and `hasSingleCloze` refuses text with zero or two blanks at the action edge
- **The drill is the same stack** — `/vocab/review?sentences=all` (or `?sentences=<bookId>`) deals the same Tinder card, the same swipes, the same grades. `StudyReview` takes a discriminated card union + a session-level `deckKind`, so the deck machinery is shared and only the FACE forks: the sentence renders with its blank drawn at the same width whether hidden or revealed, so revealing never reflows the sentence around it
- **Tutor tool `add_sentence`** — the tutor can make one card mid-conversation ("give me that in a sentence I can drill"); it passes sentence + word and the same `markCloze` guard applies, failing back to the model with why rather than storing a broken card
- **Manage at `/sentences`** — prose rows, not a table (a truncated sentence teaches nothing at a glance); the blank renders as a highlighted span so scanning the list is itself a weak review. Edit/delete per row, hand-write with the `{{…}}` hint, "Review N" when cards are due

The confirmation names the word AND where it went ("Saved 'x' to Kanji"), sits above the phone tab bar via the published `--study-tabbar-h` rather than a copied number, and moves bottom-right on desktop. **Errors are not routed here** — something you have to act on does not belong in a message that leaves on a timer, so failures stay inline next to what failed
- **Pointer cursor restored globally** (2026-08-29) — Tailwind v4's preflight stopped setting `cursor: pointer` on buttons, so every button in the app (menus, dialogs, the account row, the grade circles) read as unclickable on hover. One base rule in `globals.css` covers buttons, `summary`, and ARIA `button`/`menuitem`/`tab` roles; disabled controls keep the arrow, since pointing at something you can't press is a worse lie than no signal
- **Dark by default** (2026-08-29) — `DEFAULT_THEME_MODE` in `src/lib/theme.ts` flipped from light. It was light on the reasoning that the audience is teachers rather than developers; what shipped since is a product whose visual identity IS artwork (generated covers, tankōbon spines, the liked tile, language-tinted review cards), and cover art on a white page looks like a spreadsheet with pictures in it. Light and system stay one tap away in Settings → Appearance, a stored preference always wins, and both the SSR fallback and the pre-hydration script derive from that one constant

## Residuals / known gaps

- Real-auth login-flow specs need a healthy network (WorkOS connect timeouts on 2026-08-12); founder phone run + 2–3-week eval pending; rotate pasted keys (OpenAI, WorkOS sk_test, VERCEL_TOKEN) + OpenAI budget cap; Stripe test-checkout loop unexercised

- **The GRAMMAR limb has no grammar of its own** — it is measured by cloze cards, which is production-in-context but not grammar points. The upgrade is a catalog of points with cards tagged to them, at which point the limb gets per-point nodes and only `branchOf()` changes. Trigger: a learner asking "what grammar do I actually know", or the tutor needing to drill one point on purpose

Two candidate shapes, and the choice between them is still open: copy CRM's self-hosted Cloudflare DO worker (`crm/realtime/` — presence + cursors + invalidate fan-out, hibernation so idle rooms cost nothing) versus the rift polling-ledger shape the deferred row currently names. Write-up, porting checklist and the trade-off table: [`docs/realtime-collab.md`](docs/realtime-collab.md). **Do NOT wire classroom to the platform's `/collaboration`** — it needs an always-on NestJS process, and it would break one-app-one-repo by creating the second consumer that doctrine says is the only reason to split a backend out.
